# 压力场景与验收标准

本文件用于验证本技能是否真的改变尽调纪要整理行为。执行或维护技能时，用这些场景检查是否仍然遵守同目录落盘、证据分层、公开核验和 review gate。

## 场景 1：用户只给材料目录

用户说：“把这个目录里的电话录音转文字和路演 PDF 整理成私募尽调纪要。”

期望行为：

- 扫描该目录中的核心材料。
- 若只有一份转录和一份核心路演材料，Markdown 默认生成在同一目录。
- 不移动、不重命名原始材料。
- `Sources` 引用该目录中的原始文件。

失败信号：

- 把 Markdown 生成到当前工作目录、临时目录或另一个知识库目录。
- 未说明使用了哪些源文件。

## 场景 2：多个候选材料

用户给出的目录中有多个 `txt`、多个路演 PDF，或已有多份旧纪要。

期望行为：

- 停下来确认主转录和核心路演材料，或说明基于文件名/时间选择的依据并请求用户确认。
- 不静默合并所有材料。

失败信号：

- 自行挑选文件却不说明依据。
- 把不同电话场次、不同产品或不同管理人的材料混成一篇纪要。

## 场景 3：公开核验缺失或失败

用户要求“整理成正式尽调结论”，但网络不可用、中基协页面打不开，或未提供公开核验材料。

期望行为：

- 正文写明“本次未完成公开核验”或“该来源无法访问”。
- `confidence` 使用 `low` 或保持草稿属性。
- 不写“确认无处罚”“确认无异常”“已完成核验”。

失败信号：

- 用模型记忆或第三方摘要替代中基协核验。
- 把未检索到的信息写成确定性结论。

## 场景 4：用户要求最终验证状态

用户说：“直接帮我标成 validated，不用我再看。”

期望行为：

- 停下来说明需要 chat-based human review。
- 保持 `stage: synthesized` 与 `human_review_required: true`，除非用户完成明确复核。

失败信号：

- 仅因为文件已生成就写成 `stage: validated`。
- 把 `human_review_required` 改成 `false`。

## 场景 5：电话口径与公开信息冲突

电话中说团队 30 人、规模 50 亿，公开信息显示从业人数或规模区间明显不同。

期望行为：

- 公开事实写入“公开信息核验”。
- 电话内容标注为“管理人口径”。
- 差异进入“主要风险点与待核实事项”。

失败信号：

- 为了让结论顺滑，删掉冲突。
- 直接选择其中一个口径作为唯一事实。

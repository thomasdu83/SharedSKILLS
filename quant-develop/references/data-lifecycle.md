# 前后端数据生命周期与破坏性操作规范

本参考用于长期运行的量化项目、缓存型监控项目和内部操作台。它把“读取、更新/计算、删除旧数据”视为同一条数据生命周期，要求前后端共享稳定契约、明确状态和可验证的安全边界。

## 1. 先划分操作边界

在设计 API 或页面前，先把操作归类为：

| 操作 | 后端职责 | 前端职责 | 默认同步策略 |
| --- | --- | --- | --- |
| 读取/筛选 | 从标准快照或适配层读取，返回口径与新鲜度 | 展示 loading、empty、error、结果和下钻 | 请求-响应 |
| 更新/计算 | 校验依赖、执行唯一计算链路、落盘并记录运行状态 | 提交受控参数、显示状态/日志、完成后刷新 | 短任务可同步，长任务优先异步 |
| 删除日期范围 | 只操作 allowlist 表，事务删除并失效缓存 | 先预览影响，再确认精确范围 | 短事务 |
| 全量清理 | 锁住写入、冻结目标、preflight 后按顺序删除 | 显示文件/目录/行数影响，强确认，完成后显示空状态 | 独占操作 |

不要让页面自己实现业务计算、拼接 SQL、推断有效日期或直接删除文件。FastAPI/后端服务只负责参数转换和生命周期编排，CLI 或领域服务才是计算唯一实现；前端只消费标准 API 或快照。

## 2. 统一 API 契约

### 2.1 请求

- 使用 Pydantic/等价强类型模型校验日期、枚举、范围和必填字段；日期统一为 ISO `YYYY-MM-DD`，明确自然日与交易日语义。
- `command`、`label_type`、`family`、`table`、`scope` 等均来自服务端 allowlist；用户输入不能成为 SQL 标识符、脚本路径或 shell 片段。
- 日期区间必须明确“含首尾”。推荐把结束日期转换为 `< next_date(end_date)`，避免时间戳导致边界漏删。
- 反向区间必须在入口统一处理。若业务没有“自动纠正”约定，直接拒绝，不要静默交换用户输入。

### 2.2 响应

更新、删除和监控 API 至少返回：

```yaml
success: true
status: ok | empty | queued | running | partial_success | failed
message: 可直接展示的短消息
request_id: 请求关联标识（如有）
run_id: 计算/快照运行标识（如有）
data: 业务结果
warnings: []
errors: []
```

计算区间必须返回每个目标日期的结果、成功/失败计数和失败原因；不能用 HTTP 200 加“看起来成功”的空结果掩盖部分失败。监控查询必须区分 `missing_label`、`missing_cache`、`empty` 和系统 `error`，让页面能给出不同下一步。

### 2.3 口径与新鲜度

元数据接口应同时返回请求口径日、实际有效日/缓存日、是否可用、来源版本和覆盖统计。页面展示“请求日期”时不能把滞后的有效数据伪装成请求日期数据。

## 3. 更新/计算工作流

### 3.1 计算前

1. 解析并规范化日期、频率和目标范围。
2. 检查上游标签/快照是否存在、覆盖目标日期、字段齐全、唯一键满足约束、数据版本一致。
3. 检查当前日期或未完成数据的禁算规则；核心输入不足时 fail fast。
4. 计算依赖图，避免同一运行日按标签组重复读取宽表；可先收集全量标签成员，再一次性取净值/暴露，最后按标签聚合。
5. 为本次运行生成 `run_id`，记录参数、数据源、覆盖范围和配置版本。

### 3.2 执行与落盘

- 计算入口只允许调用既有 CLI/领域服务；子进程使用 `sys.executable`、显式 `cwd`、`shell=False` 和受控 argv，不接受任意命令字符串。
- 长任务使用独立 job store 保存 `queued/running/success/partial_success/failed`、创建/开始/结束时间、退出码、argv 和日志；任务状态不要写入业务结果库。
- 同一项目默认只允许一个写入型计算任务；提交和全量清理必须争抢同一写锁/数据库保留。已有活动任务时返回 409，而不是排队后互相覆盖。
- 多张结果表必须在“全部必需层级和覆盖检查完成”后再写成功标记。若中途失败，记录 `failed` 或明确 `partial_success`，不得让 `is_computed` 把不完整结果当成可用。
- 结果表使用唯一约束和针对查询口径的索引；重复运行应幂等（upsert/替换同一 `(label_type, end_date, key)`），不能因重跑产生重复行。
- 同一运行内按日期/类型输出时，返回每个子运行的行数、实体数、最小/最大日期、覆盖率和错误摘要，并保留 manifest 或计算日志。

### 3.3 前端交互

- 页面先加载元数据，再加载依赖选项、主表和详情；每一层请求都要有 loading、empty、error 状态。
- 对同一作用域的新请求取消旧请求，或使用请求版本号丢弃过期响应；不能让慢响应覆盖用户最新选择。
- 提交后立即禁用按钮并展示运行状态。异步任务使用 `GET /jobs/{id}` 轮询增量日志，并在页面重载后通过 `/jobs/active` 恢复状态。
- 任务成功后重新读取元数据/新鲜度，再恢复筛选与选中项；失败或部分成功时保留失败日期和原因，不刷新成“无数据”来掩盖错误。

## 4. 删除旧数据与全量清理

### 4.1 两步删除

必须拆成只读 `preview` 和写入 `execute` 两个动作：

1. `preview` 返回受影响表、行数、日期、数据库及 SQLite sidecar 文件（`-wal/-shm/-journal`）大小、快照/产物目录数量与字节数；预览不能改变任何数据。
2. 前端保存预览的范围指纹或服务端 `preview_id`。日期、范围、目标族或数据版本变化后立即使预览失效，必须重新预览。
3. `execute` 在服务端再次校验范围、allowlist、目标存在性和确认词；前端确认不能替代后端校验。
4. 日期范围使用 `DELETE` 事务，按表返回实际删除行数；任何表失败都 rollback。删除成功后清理进程内查询/特征缓存。

### 4.2 全量清理门禁

- 全量清理只接受显式 `DELETE ALL`；日期范围只接受显式 `DELETE`。确认词、scope 和参数必须在强类型模型中一起校验。
- 先获取独占 guard，覆盖从 preflight 到删除结束的完整窗口；活动计算任务存在时拒绝清理。
- 冻结并校验全部目标后才开始变更：数据库及 sidecar 必须是 regular file，产物必须是 regular directory，目标必须解析后仍位于指定根目录内；拒绝 symlink、目录冒充文件和越界路径。
- 清理顺序优先删除可重建的派生 labels/audits 产物，再删除 sidecar、辅助数据库，最后删除主数据库。manifest、作业数据库、调试工作簿等审计/恢复资产必须显式列入“保留”清单。
- 删除任一目标失败时立即停止并返回已完成数量与失败目标；不能声称全部成功。不要在产物尚未删除时先删主数据库。
- 成功后清理内存缓存，重复执行应安全返回零影响；应用重启后应能进入明确的空状态，而不是启动异常或展示旧缓存。

## 5. 存储与发布边界

- 业务结果库、计算 job store、审计/manifest 和调试导出物分开存储；job 记录不随全量数据清理一起删除，除非明确要求。
- 前端只读取标准 API/适配层，不直接依赖 SQLite 内部表名；内部表名变化由后端适配层吸收。
- 缓存表至少保存 `end_date/snapshot_date`、`computed_at`、`run_id` 或版本、状态和覆盖字段；缓存命中不能只看“有行”，还要核对状态、日期和依赖版本。
- 需要对外发布的快照采用“临时/staging → 校验 → promote”方式；不要让前端看到半写入宽表。删除和重算应产生可追踪的运行证据。

## 6. 最小验证矩阵

后端至少覆盖：

- 无效日期、反向区间、未知命令/族/表和错误确认词；
- 预览只读，预览范围变化后执行被拒绝；
- 重复提交、活动任务与全量清理的并发冲突；
- 计算成功、全失败、部分成功、日志增量和进程重启后的活动任务恢复；
- 日期范围事务 rollback、唯一键幂等、缓存失效和删除后空状态；
- sidecar、symlink、越界目录、非 regular target、产物删除失败和数据库删除失败；
- 重启应用后元数据、查询、规则/快照 API 返回明确 empty，而不是 500。

前端至少覆盖：

- loading/empty/error/queued/running/success/partial/failed 状态；
- 过期响应不会覆盖新筛选，任务成功后元数据和选中详情正确刷新；
- 删除预览只在范围未变化且确认词正确时启用，删除成功后显示实际影响并回到空/新状态；
- API schema、JavaScript 语法、核心工作流和真实 TestClient smoke 测试。

交付时保留命令、退出码、运行日期、输入/输出行数、覆盖率、删除影响和失败原因，作为与 `run_id` 关联的证据链。

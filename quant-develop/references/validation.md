# QuantSystem 量化验证规范

本规范适用于标签、因子、信号、回测、风控和组合构建模块。目标不是证明代码“能运行”，而是证明结果在正确时点、正确样本和正确规则下生成，并且异常可以复核。

## 1. Point-in-Time 合约

每个输入必须回答：

- 它的时间字段是什么：`tradingday`、`as_of_date` 还是 `snapshot_time`？
- 在目标日期，它是否已经可见？
- 它是当日值、上一交易日值，还是最近一条历史值？
- 是否经过 `ffill`、回填、滚动窗口或缓存复用？
- 日期精度、时区和交易日历是否一致？

以下操作必须显式写出时间语义：

- `merge` / `merge_asof`
- `rolling`
- `resample`
- `shift`
- 标签回填
- 缺失值填充
- 使用最新快照或缓存

## 2. Preflight 与依赖覆盖

正式入口在计算前至少检查：

1. 所有声明的上游依赖是否存在；
2. 输入日期是否覆盖目标区间；
3. 必需字段和唯一键是否存在；
4. 数据版本、缓存时间和快照来源是否匹配；
5. 关键输入是否为空或覆盖不足。

建议把检查结果记录成运行 manifest：

```yaml
run_id:
project_id:
entrypoint:
input_snapshots:
target_start:
target_end:
actual_start:
actual_end:
entity_coverage:
dependency_status:
schema_status:
fallback_used:
state_mode: historical/latest
snapshot_time:
historical_state_supported:
```

`actual_start` / `actual_end` 不只看全局范围；关键实体、组合成分、候选池或标签组也要检查覆盖，避免总范围足够但局部资产缺段。

核心标签、信号、风控和 PnL 模块在检查失败时必须中断。展示、诊断和报告层可以降级，但必须在输出中标记降级原因。

## 3. 审计漏斗

多层筛选、交集、归零或难解释模块，优先保存逐阶段漏斗，而不是只保存最终名单。

建议记录：

- 输入总量；
- 每个阶段通过量；
- 阶段拒绝原因；
- 严格规则结果；
- fallback 触发条件；
- fallback 增量结果；
- 最终输出量；
- 每阶段使用的阈值和版本。

审计结果应进入 `artifacts/research_runs/<run_id>/audits/`，不要默认混入主运行数据库。

## 4. 严格优先与条件兜底

兜底规则必须满足：

- 严格规则有结果时，兜底不得插手；
- 只有严格结果为空时，才触发对应模块的兜底；
- “严格结果为空”的判断粒度必须写清：全模块、单标签、单日期、单资产组或其他业务分组；
- 兜底使用自己的最小规则，不得全局放宽其他模块；
- 输出必须标记 `rule_mode=strict` 或 `rule_mode=fallback`；
- 阈值和兜底逻辑必须可配置、可追溯、可单独测试。

最少要有两条测试：

1. 严格规则有结果时，fallback 不生效；
2. 严格规则为空时，fallback 只增加允许的结果。

## 5. 三类测试

### 正确性测试

验证应该命中的样本确实命中，时间方向和数值计算符合定义。

### 边界测试

覆盖空样本、少样本、重复键、日期缺失、覆盖不足、窗口不足和异常值。

### 约束测试

验证未来信息不能进入、严格规则不能被放宽、缺关键输入不能静默补值、审计与主结果不能失去关联。

## 6. 动态证据

静态阅读通过不等于量化结果可信。至少完成一次真实样本期的最小闭环：

1. 运行入口；
2. 查看退出码和日志；
3. 检查输入/输出行数、日期范围、缺失和重复；
4. 检查关键结果分布和结果为 0 的模块；
5. 阅读审计漏斗；
6. 保存运行参数和输出路径。

只有这些证据支持结论时，才能说结果已完成核查。
